# `==` 与 `===` 的区别（PHP 弱类型比较陷阱与 PHP 8 改动）

> 难度：★★~★★★★　适用岗位：工程师 → 架构师
>
> 这是一道几乎每场 PHP 面试都会出现的"入门题"，但想答到加分项非常难。本文按"问题陈述 → 考察意图 → 分层答案 → 常见追问 → 代码示例 → 延伸阅读"六段式给出完整答题思路。

## 一、问题陈述

> PHP 里 `==` 和 `===` 有什么区别？为什么 `0 == "abc"` 在 PHP 7 里是 `true`，到了 PHP 8 却变成了 `false`？你在实际项目里踩过哪些比较相关的坑？

## 二、考察意图

面试官借这道题通常想验证三件事：

1. **基础扎实度**：你是否真正理解"类型转换"在 PHP 里是如何发生的，而不只是背一句"`==` 不比较类型"；
2. **线上经验**：你是否在真实项目里因为松散比较踩过坑（例如 `in_array` 漏判、`switch` 命中错误分支、JSON 解析后数字变字符串）；
3. **对现代 PHP 的跟进**：你是否了解 PHP 8 的 "Saner string to number comparisons" RFC 改动，以及这对老项目升级意味着什么。

一个只能答出"一个比较值、一个比较值和类型"的候选人是工程师（★★）；能说清转换规则 + 至少 3 个真实陷阱的是高级工程师（★★★）；能自然带出 PHP 8 改动、并给出老代码排查方案的是架构师（★★★★）。

## 三、参考答案（三层）

### 3.1 基础回答（★★）

- `==`：**松散比较**（loose comparison）。两边类型不一致时，PHP 会按一套内置规则先做**类型转换**再比较值；
- `===`：**严格比较**（strict comparison）。类型必须一致、值也必须相等，才返回 `true`；
- **工程建议**：默认一律使用 `===`，除非你明确知道自己就是要做"语义宽松"的比较。`!=` / `!==` 同理。

```php
var_dump(1 == "1");   // true  —— "1" 转成 int 1
var_dump(1 === "1");  // false —— 类型不同
var_dump(1 == true);  // true
var_dump(1 === true); // false
```

### 3.2 进阶回答（★★★）

松散比较之所以容易踩坑，是因为 PHP 的**类型转换表**非常"宽容"。下面这些场景在任何一个 PHP 项目中都可能出现：

| 表达式 | PHP 7 结果 | PHP 8 结果 | 原因 |
| --- | --- | --- | --- |
| `0 == "0"` | true | true | "0" 转 int 0 |
| `0 == ""` | **true** | **false** | PHP 7 时空串转 0；PHP 8 改为字符串比较 |
| `0 == "abc"` | **true** | **false** | PHP 7 时非数字串转 0；PHP 8 改为字符串比较 |
| `0 == null` | true | true | null 转 int 0 |
| `"1" == "01"` | true | true | 都是数字串，转数字比较 |
| `"10" == "1e1"` | true | true | 科学计数法都识别为 10 |
| `100 == "1e2"` | true | true | 同上 |
| `false == []` | true | true | 空数组转 bool false |
| `null == false` | true | true | 都转 bool |

**几个特别容易中招的陷阱：**

1. **`in_array` / `array_search` 默认走 `==`**：`in_array(0, ['abc', 'def'])` 在 PHP 7 里会返回 `true`（因为 `"abc" == 0` 为 true）。这是很多 SQL 注入、权限绕过漏洞的根源，**一定要传第三个参数 `strict: true`**。
2. **`switch` 用的是 `==`，`match` 用的是 `===`**：`switch (0) { case "abc": ... }` 在 PHP 7 中会命中，是历史上无数隐蔽 bug 的来源。PHP 8.0 引入的 `match` 表达式使用严格比较，行为更安全。
3. **JSON / HTTP 解析后类型丢失**：前端传过来的 `"0"`、`"false"`、数据库返回的字符串数字、`$_GET`/`$_POST` 里的所有值都是字符串，一旦和数字做 `==` 比较，极易出现"看起来对但结果错"的情况。
4. **`null` 与 `false` 的语义混淆**：`strpos($haystack, $needle) == false` 在找到位置 0 时也会为 true，必须用 `=== false`。这是 PHP 官方手册专门提醒过的经典陷阱。

### 3.3 加分项（★★★★ 架构师视角）

要把这道题答到架构师水平，可以主动抛出以下三个点：

**1）PHP 8 的 "Saner string to number comparisons" RFC**

PHP 8.0 修改了"数字与非数字字符串"的比较规则：

- **PHP 7 及之前**：把字符串转成数字再比较（非数字串视为 0）；
- **PHP 8 开始**：如果一边是数字、另一边是**非数字字符串**，则把数字一侧转为字符串后进行**字符串比较**。

这意味着 `0 == "abc"` 在 PHP 8 里是 `false` —— 终于符合直觉了。但它也是**老项目升级到 PHP 8 的一个隐性兼容风险**：

```php
if ($role == 0) { // 如果 $role 是字符串 "admin"
    // PHP 7: true，意外命中"普通用户"分支
    // PHP 8: false，行为变更
}
```

**2）老项目升级的排查策略**

架构师被问到这里通常会补一句"我们在升 PHP 8 时是这么做的"：

- 用 **Rector** 的 `PHP80` 规则集批量检测与重写；
- 用 **PHPStan / Psalm** 的严格模式扫描所有 `==` / `!=`，逐步替换为 `===` / `!==`；
- 灰度发布 + 回归测试，重点盯 `switch`、`in_array`、`array_search`、`strpos`、`filter_var` 相关路径；
- 约定团队规范：**新代码一律禁用 `==`**，用 `php-cs-fixer` 的 `strict_comparison` 规则自动化保障。

**3）更深一层：为什么 PHP 要保留松散比较？**

并非 PHP 设计者"水平不高"，而是历史上 PHP 的主要输入来源是 **HTTP 请求**（`$_GET`、`$_POST`、表单），这些值**天生就是字符串**。松散比较是当时"让新手也能写出能跑的代码"的设计取舍。今天我们有了类型系统、严格模式（`declare(strict_types=1)`）、DTO、验证层，松散比较的价值已经被大幅稀释 —— 这也是 PHP 8 敢于调整比较规则的底气。

## 四、常见追问

### 追问 1：`in_array` 踩过哪些坑？如何防御？

**答**：默认松散比较导致 `in_array($userInput, $whitelist)` 在白名单是字符串数组时被绕过。例如：

```php
$whitelist = ['admin', 'editor', 'user'];
var_dump(in_array(0, $whitelist));                // PHP 7: true，PHP 8: false
var_dump(in_array(0, $whitelist, strict: true));  // 任何版本: false
```

**防御**：

1. 永远传 `strict: true`；
2. 团队里直接用 PHPStan / Psalm 的 `checkMissingIterableValueType` 之类规则强制；
3. 涉及权限判断时优先使用**关联数组键检查** `isset($whitelist[$role])`，既避开 `in_array`，又是 O(1) 查找。

### 追问 2：`switch` 和 `match` 到底怎么选？

**答**：

| 维度 | `switch` | `match` |
| --- | --- | --- |
| 比较方式 | `==` 松散 | `===` 严格 |
| 语法形态 | 语句 | 表达式（有返回值） |
| 是否 fall-through | 需要 `break` | 无 fall-through |
| 未命中 | 需手写 `default` | 抛 `UnhandledMatchError` |
| 适用 | 兼容老代码 | 新代码首选 |

生产代码中，**新代码强烈建议用 `match`**：它天然避开了松散比较、fall-through、忘写 break 这三个历史包袱。

### 追问 3：`declare(strict_types=1)` 和 `===` 是同一件事吗？

**答**：**不是**。

- `strict_types=1` 影响的是**函数参数和返回值的类型检查**：声明后，`function foo(int $x)` 被传入 `"1"` 会直接抛 `TypeError`；
- `===` 影响的是**运行时比较操作**。

两者是"同一种工程理念"（不要依赖隐式转换）在不同维度的落地，建议同时启用。

## 五、代码示例：一份给新人的"比较速查表"

```php
<?php
declare(strict_types=1);

// ✅ 推荐写法
if ($role === 'admin') { /* ... */ }
if (in_array($id, $allowed, strict: true)) { /* ... */ }
if (strpos($email, '@') !== false) { /* ... */ }
$status = match ($code) {
    200, 201 => 'ok',
    404      => 'not_found',
    default  => 'error',
};

// ❌ 易错写法
if ($role == 0) { /* 隐藏陷阱：字符串 $role 也可能命中 */ }
if (in_array($id, $allowed)) { /* 松散比较可能误通过 */ }
if (strpos($email, '@')) { /* 位置 0 会被当成 false */ }
switch ($code) {
    case 200: $s = 'ok';         // 忘写 break 就会 fall-through
    case 404: $s = 'not_found'; break;
}
```
